# Convenium.Design Loadout Sync

## Why this exists

A per-agent skill loadout has three write targets and they must never drift:

1. `.claude/agents/<agent>.md` — a regenerated marked block so the agent's own file
   literally lists the shortlist the active setup assigns it.
2. `<project>/.convenium-design/loadouts/<id>.json` — a copy of a **custom** setup (built-in
   presets already live in `profiles/loadouts/` and are not copied).
3. `<project>/.convenium-design/loadouts/active.json` — the pointer to whichever loadout is live.

`scripts/apply-loadout.ps1` is the reference implementation of the regeneration
algorithm. This skill and `dashboard/js/fs-write.js` mirror it exactly. When an agent
does loadout work it runs the script; a human clicking **Save** in the dashboard runs the
JS mirror; both must yield the same bytes. Do not hand-edit between the markers, and do
not add a second write path — same discipline as `convenium-design-dashboard-sync` for `state.json`
(`architecture.md` §6, §12).

## The marker block

```
<!-- CONVENIUM.DESIGN:ACTIVE-LOADOUT:START -->
**Active loadout ("<name>"):** <id>, <id> (<variant>), … This is the shortlist the
dashboard's active setup assigns to this agent - still load only the one or two entries
the task at hand needs; the catalog's normal "load the minimum" rule is unchanged.
Regenerated by convenium-design-loadout-sync / scripts/apply-loadout.ps1 - do not hand-edit
between the markers.
<!-- CONVENIUM.DESIGN:ACTIVE-LOADOUT:END -->
```

- Skills render as the catalog `id`, or `id (variant)` when a variant is set.
- The block sits directly under each file's first skills heading
  (`## Skills — …` / `## Your skills — …`), or its first `##` heading otherwise.
- An agent **not** named in the loadout has its block **removed** — it falls back to its
  catalog default.

## Operations

**Activate a loadout** — `{loadoutPath}`. The path resolves against
`profiles/loadouts/loadout.schema.json`.

1. Prefer running the script:
   `pwsh scripts/apply-loadout.ps1 <loadoutPath>`.
   It validates, rewrites only the agent files that change, and prints a
   "Wrote & verified N file(s)" report with a truncated before/after of each block.
2. If PowerShell is unavailable, do the identical procedure by hand (see **Procedure**).

**Clear the active loadout** — `pwsh scripts/apply-loadout.ps1 -Clear`. Removes every
marked block and sets `active.json` `activeLoadoutId: null`.

**Save a custom setup** — the dashboard writes the setup JSON to
`<project>/.convenium-design/loadouts/custom-<slug>.json` (the `custom-` prefix is mandatory — it
keeps a user setup from ever colliding with a shipped preset id), then activates it via
the same path.

## Procedure — every operation follows this exactly

1. **Validate first, write nothing on failure.** For every `agents.<name>.skills[].id`:
   it must resolve to an entry in `dashboard/data/skill-catalog.json`, and that entry's
   `eligibleAgents` must contain `<name>`. A `variant` must be in the entry's
   `variants[]`. Any failure → report all of them and stop. This is the same check
   `scripts/verify-roster.ps1` runs at build time.
2. **Read each target agent file** before touching it. Detect its line-ending
   convention (some agent files are CRLF, some LF) and preserve it.
3. **Regenerate the block** for each of the 12 roster agents:
   - agent in the loadout with ≥1 valid skill → insert/replace its block;
   - agent absent → remove its block if present, else no-op.
4. **Replace only the text between (and including) the markers**, plus the single blank
   line bracketing each side — never the surrounding prose. Applying the same state
   twice must produce byte-identical output.
5. **Write via temp-file-then-rename** (`<file>.tmp` → rename over `<file>`), and only
   when the content actually changed. UTF-8, no BOM.
6. **Read each changed file back** and confirm the block matches what was intended —
   the dashboard shows this as its "Wrote & verified N files" proof panel, not just a
   success toast.
7. Write `active.json` (`{schemaVersion: 1, activeLoadoutId: <id|null>, activatedAt:
   now}`), and for a non-built-in setup, the setup JSON copy under
   `.convenium-design/loadouts/`.

## What this skill does not do

- It does not decide *which* loadout should be active — the user or the dashboard picks
  that; this skill records it.
- It does not touch `state.json` — that is `convenium-design-dashboard-sync`'s job. Comparing a
  loadout's shortlist against `state.json`'s `skillsLoadedThisRun` (the "did the run
  honour the setup" check) is a **read** the dashboard does, not a write either skill
  performs.
- It never commits anything under `.convenium-design/` — that is personal run state
  (`CLAUDE.md` "Never").
